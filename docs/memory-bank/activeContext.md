## FIX: онбординг пропускался — привязка к `is_new_user` вместо состояния (2026-09-30) ✅

**Симптом (юзер 456371881, telegram_id, тестовый аккаунт):** зашёл напрямую
через бота без инвайт-ссылки, приложение открылось мимо обязательного
создания первой доски.

**Причина — не «баг редиректа», а необратимость флага.** Онбординг решался по
`is_new_user`, а этот флаг означает не «нужна доска», а «профиль создан в
этом конкретном HTTP-запросе». В `/api/init` ветка «профиль УЖЕ есть»
(стр. 230–245) жёстко отдаёт `is_new_user: false`, **не различая случая
«есть доски» и «досок ноль»**.

Цепочка бага:
1. `/start` без кода → бот шлёт приветствие, профиль **не** создаётся;
2. вход в TWA → `/api/init` → профиля нет → `is_new_user: true` →
   `app/page.tsx` → `/board/create`;
3. пользователь прерывает создание (закрыл TWA / перезагрузил);
4. следующий вход → профиль **уже есть** → `is_new_user: false`,
   `workspaces: []` → `app/page.tsx` уводит на `/flowboard`;
5. `needsOnboarding` содержал `&& isNewUser` → модалка не показывается.

Итог: **пустая доска вместо формы, выхода нет** — состояние «профиль есть,
досок ноль» достигается один раз и больше не меняется. Именно это и есть
наблюдаемый баг; `DataContext.tsx:438-445` этот случай грузил корректно
(фикс 2026-09-07), поэтому вёрстка была в порядке — не было лишь формы.

**Решение.** Условие выведено из СОСТОЯНИЯ, а не из факта прошлого:
`src/lib/onboarding.ts` → `needsBoardCreation(data)` = `workspaces.length === 0`.
Общая функция вместо правки в двух местах, потому что расхождение этих двух
мест и породило баг. `is_new_user` в контракте оставлен, но роутинг от него
отвязан.

Правило, которое стоит запомнить: **обязательный шаг нельзя привязывать к
необратимому событию.** Профиль создаётся один раз и навсегда; доска —
пока её нет. Привязка онбординга к «профиль создан» делает прерывание
необратимым.

**Крайние случаи, проверенные отдельно:**
- **инвайт**: `/api/init` для нового юзера с валидной ссылкой отдаёт
  `workspaces: [{ id, name: '', slug: '' }]` → длина 1 → онбординг **не**
  показывается (задумано);
- **ошибка авторизации**: `data === null` → `needsBoardCreation` возвращает
  `false`, иначе был бы редирект на создание доски вместо экрана ошибки.
  Защита живёт в самой функции, а не в вызывающем коде;
- **`hasNavigatedRef` в `app/page.tsx` сохранён** — он гасит повторный
  эффект от `refresh()` сразу после создания доски.

**Попутно (тот же класс дефекта):** `src/lib/bot/onboarding.ts` — вставка в
`workers` не проверяла `error`, и молчаливая ошибка оставляла профиль без
доски. Теперь `error` проверяется и бросается; вызывающий `try/catch` в
`bot/webhook/route.ts` уже отправляет пользователю сообщение об ошибке.
Также удалён мёртвый проп `isNewUser` в `FlowBoard` (объявлен, но не
использовался — модалку рендерит страница).

**Валидация:** `npm test` 637/637 (было 630): +6 `tests/lib/onboarding.test.ts`

## SUB-01 · Stage 6: права на подзадачу — владение от РОДИТЕЛЯ (2026-09-30) ✅



Владелец спросил, не забыли ли удаление подзадачи. Само удаление было, и
проверка вскрыла **реальный баг прав**, а не отсутствующую фичу.

**Баг 1 — UI обещал то, что сервер отвергал.** `DELETE /api/tasks/[id]` считал
права по `created_by` САМОЙ подзадачи, а UI показывал кнопку по правам на
**родителе** (`canEdit`). Отсюда два расхождения:

- исполнитель родителя (`canEdit=true`, `canDelete=false`) видел кнопку удаления
  и получал 403;
- если подзадачу создал админ в чужой задаче, **автор задачи терял** право её
  удалить — потому что `created_by` подзадачи = админ, а не он.

**Решение:** `subtaskOwnerRow()` в `src/lib/subtasks.ts` — права на подзадачу
считаются по родителю (его `created_by`/`assigned_to`). Подзадача — часть
жизненного цикла задачи, значит и права принадлежат задаче. Правило применено в
PATCH и DELETE. В PATCH `column` намеренно остаётся СОБСТВЕННОЙ подзадачи:
от него зависит self-claim, и «взять подзадачу в работу» решается по подзадаче.

UI: `SubtasksSection` получил отдельный проп `canDeleteSubtask`
(`taskPermission.canDelete`) вместо `canEdit`. Смешивать их нельзя — это и был
корень расхождения.

**Баг 2 — обход запрета агента через PATCH.** Правило «подзадаче нельзя назначить
AI-агента» стояло только в `POST /subtasks`. Но `PATCH /api/tasks/[id]` — общий
путь назначения, и он тип исполнителя не проверял. Последствие было не
косметическим: `trg_dispatch_outbox_on_assign` кладёт задачу в `dispatch_outbox`
при назначении **агенту**, то есть подзадача уходила агенту в работу в обход
`.is('parent_task_id', null)` в `getTasksByColumn`. Гард перенесён в PATCH,
переиспользует `canBeSubtaskAssignee`.

**Проверено БД:** DELETE-триггеров на `tasks` нет — удаление не блокируется.
`assign_task_number` и `enqueue_duplicate_check` защищены гардами (Stage 1).
`notify_task_assignment` гарда не имеет и срабатывает на создание подзадачи с
исполнителем — это желаемо (исполнитель должен узнать о назначении), но текст
уведомления говорит «задача», а не «подзадача» (SUB-01.7).

**Тесты: 614/614** (было 602). Новый `tests/api/tasks/subtaskDeletePermission.test.ts`
(8) — DELETE/PATCH на подзадаче; мок различает строки по `eq('id', …)`, иначе
невозможно проверить, что права считаны по РОДИТЕЛЮ. +4 юнит-теста на
`subtaskOwnerRow`.

**Мутациями доказано, что тесты ловят именно эти баги:**

| Что отключил | Что упало |
|---|---|
| `ownerRow = taskData` (права по подзадаче) | **2** теста |
| гард «подзадача» в PATCH | **1** тест |

**Смок на ПРОДЕ выполнен (был отменён из-за токена — теперь токен рабочий).**
Сценарий 1 (удаление): создана временная подзадача + комментарий → DELETE →
проверки. Сценарий 2 (нумерация): две подзадачи (1, 2) → удалена первая.

| Проверка | Результат |
|---|---|
| `task_number` подзадачи | `NULL` (как и задумано в ADR) |
| удаление подзадачи | вернуло 1 строку, строк стало 0 |
| комментарий подзадачи после удаления | 0 — `ON DELETE CASCADE` работает |
| родитель после удаления подзадачи | жив (1) |
| позиции после удаления №1 | выжившая осталась с `index=2` — **не сдвинулась** |
| дубль `subtask_index` | отвергнут: HTTP 409, `pg_code=23505` |
| мусор после смоука | 0 задач, 0 комментариев; всего задач 56 (как до смоука) |

То есть решение «нумерация max+1, позиции не сдвигаются» подтверждено на живых
данных, а не только юнит-тестом.

**Два способа выиграть время, запомнить на будущее:**

1. **Токен оказался валиденным — его не понимал старый CLI.** Формат новых PAT:
   `sbp_v0_` + 40 hex. Установленный `supabase` 2.109.1 его отвергает
   (`Invalid access token format`), а `npx supabase@latest` (2.118.0) —
   принимает. Если CLI «не видит токен», сначала проверь версию, а не ищи
   опечатку в токене.
2. **Смоук-скрипты для Windows PowerShell 5.1 — только ASCII.** Файл без BOM
   читается как ANSI, кириллица превращается в ошибки парсинга. Плюс:
   `ConvertFrom-Json` на массиве отдаёт один контейнер (Where-Object по нему не
   фильтрует — нужно разворачивать явно), и **без `Prefer: return=representation`
   POST возвращает пустое тело** — я из-за этого не получил id и на минуту
   оставил тестовую задачу в проде. Уборку надо делать по фильтру по title, а не
   по сохранённому id, либо всегда ставить этот заголовок.

`computeChecksum`. Значит уникальный индекс для легаси-документов бесполезен:
новый SHA-256 не совпал бы со старой строкой, и дубль прошёл бы.

**Лечение — в `doc-process`**, а не разовой правкой данных: файл там уже
скачан для чанкинга, поэтому хеш считается бесплатно и по тем же байтам, что
хешировал Route Handler. Перезаписываются **только** заведомо старые значения
(`/^[0-9a-f]{64}$/` как защита от лишней записи). Ошибка перезаписи не роняет
обработку: типичный отказ — два легаси-документа с одинаковым содержимым, и
это повод разобраться, а не помечать документ `failed`.

Проверено на проде: `checksum_604251_7552` → `98a34fd9…a8574` (64 hex),
документ вернулся в `ready` с 14 чанками. Повторная вставка того же хеша →
23505.

**Два уровня защиты, потому что одной проверки мало.** Проверка в Route Handler
даёт понятную ошибку; уникальный индекс ловит гонку (два параллельных запроса
оба увидят, что документа нет, и оба вставят) — поэтому 23505 разбирается
отдельно, а файл из Storage убирается.

**Проба в тестах — снова дала ложноотрицательный результат.** Проверка вызова
бэкфилла искала подстроку `backfillLegacyChecksum(...)`; закомментированный
вызов ей удовлетворял, и тест оставался зелёным при выключенной
функциональности. Переписано на якорь `^\s*await` с флагом `m` — он не матчит
комментарий. Это третий раз за три фазы, когда регулярка по тексту врала, и
причина одна: проверка «что-то упоминается» вместо «что-то исполняется».

## Имя человека в ленте комментариев: telegram_user_* → display_name (2026-09-16) ✅

**Баг:** в ленте «Комментарии» (RPC `get_task_feed`) агентские события от webhook

**Причина:** ветка «в» `get_task_feed` (миграция 076) возвращала `a.agent_name` как есть,
хотя webhook (`route.ts:1384`, `:1529`) уже сохранял реального человека-воркера в
`metadata.actor_worker_id`.

**Фикс (миграция 088, `088_task_feed_actor_display_name.sql`, применена):**
`CREATE OR REPLACE FUNCTION get_task_feed` — ветка «в»:
`LEFT JOIN workers w ON w.id::text = a.metadata->>'actor_worker_id'` (сравнение текстом,
без cast — безопасно для мусорных metadata),
`author_name = COALESCE(w.display_name, a.agent_name)`.
Чинит и исторические события (окно retention agent_events = 7 дней), и все будущие точки
записи без изменения webhook-кода. Реальные агенты (без actor_worker_id) — фолбэк на
agent_name, поведение не изменилось. Бонус: `SET search_path = ''` на функцию (advisor
function_search_path_mutable для get_task_feed закрыт; тело schema-квалифицировано).
Псевдо-имя в БД сохранено (легитимный аудит, решение миграции 052).

**Валидация:** RPC на живой задаче → `kind='agent', author_name='kitamoru',
body='review_requested_fix'` (было telegram_user_425693173); fallback-проверка agent-событий

## FILE-10b: Hotfix WebAppDownloadFileParamInvalid (2026-09-11) ✅

**Симптом:** ошибка `WebAppDownloadFileParamInvalid` при клике «скачать» в TWA.

**Root cause (2 дефекта):**
1. **Сервер:** прокси-URL строился как `NEXT_PUBLIC_WEBAPP_URL || new URL(req.url).origin`.
   Telegram `downloadFile` ТРЕБУЕТ `https://` — без явного env (или на http://localhost)
   URL был http → Telegram бросал исключение. Правильный паттерн уже есть в

2. **Клиент:** `WebApp.downloadFile` при невалидных параметрах БРОСАЕТ исключение,
   а не возвращает `false`. Каскад ловил только `ok === false` → исключение пролетало
   во внешний catch → показывалась ошибка вместо перехода на уровень 2 (fetch→blob).

**Fix:**
- POST `[attachmentId]/route.ts`: origin = `NEXT_PUBLIC_WEBAPP_URL || https://${VERCEL_URL}
  || origin запроса` + принудительный https (`replace(/^http:\/\//,'https://')`) — никогда
  не отдаём не-https.
- TaskViewEdit `handleDownloadAttachment`: `downloadFile` обёрнут в try/catch
  (throw → `ok=false` → уровень 2), т.е. каскад всегда продолжается.

Валидация: tsc EXIT 0 ✅. Коммит e082981.
