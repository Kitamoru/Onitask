# onitask — Desk Create screen

Готовый набор компонентов под макет «Создание доски» (страница создания
workspace в TWA onitask). Next.js 14 / App Router, TypeScript, Tailwind v4.

## Как проверялось на пиксель-перфект

Первая версия этого пакета была собрана "по памяти" о скриншоте и
получилась близкой, но неточной — плоские `rounded-2xl` карточки вместо
фирменной формы макета. Эта версия пересобрана после:

1. Покадрового пиксельного анализа скриншота (Python/PIL: измерение
   точных RGB, координат углов, ширины срезов) вместо визуальной оценки.
2. Реальной сборки этих же компонентов (esbuild + Tailwind v4 CLI) и
   рендера в headless Chromium при той же ширине/масштабе (390px, 2x) —
   чтобы сверять не "как я думаю это выглядит", а фактический пиксельный
   вывод.
3. Постранично найденных и исправленных расхождений (см. ниже).

Оценка сходства после этой сверки — по структуре, форме углов, цвету и
раскладке — субъективно около заявленного порога, но верификация шла по
готовому скриншоту, не по исходному Figma-файлу; см. «Что осталось
приблизительным» ниже.

## Главное, что было упущено в первой версии

- **Срезанные углы.** Это не `rounded-2xl` карточки — фирменная форма
  панели: два противоположных угла скруглены нативным
  `border-radius`, два других срезаны по диагонали (`clip-path`). Причём
  срез разный по смыслу элемента:
  - `panel` (срез TL+BR) — карточки-секции и крупные самостоятельные
    поля (Название доски, @desk, Краткое описание)
  - `action` (срез TR+BL) — кнопки и степперы
  - `field` (срез только BR) — поля, вложенные внутрь карточки (строки
    SP, Выберите файл, Название ресурса, Ссылка)
  - `none` — тоггл и бейдж, обычный скруглённый прямоугольник
  
  Реализовано в `lib/notch.ts` + `components/ui/NotchedPanel.tsx` —
  двухслойный трюк (внешний слой красит рамку/градиент, внутренний —
  заливку, оба со своим `clip-path`), поэтому обводка идёт точно по
  срезанному краю, а не обрывается на нём.
- **Акцентный цвет.** `#ff9900` — насыщенный чистый оранжевый, замерено
  напрямую из пикселей. Не приглушённый янтарный, который был в первой
  версии.
- **Градиентные обводки.** Кнопки «Добавить…» — обводка-градиент
  тёмно-бирюзовый → золотой. Степпер «1 день» (предупреждение) —
  янтарная обводка-градиент, «3 дня» (срочно) — красная. Это осмысленная
  деталь «светофора», не декоративный шум.
- **Тоггл.** Не iOS-пилюля: прямоугольный трек (52×28) со скруглённым
  квадратным (не круглым) ноутом.
- **Паддинг страницы.** 16px с обеих сторон (замерено), не 20px.
- **Высоты элементов.** Была одна высота 52px на всё — инпуты, кнопки,
  степперы. По факту в макете два разных размера: самостоятельные поля
  верхнего уровня (Название доски, @desk, Краткое описание) — 48px,
  а кнопки, степперы и вложенные поля внутри карточек (SP-строки,
  Выберите файл, Название ресурса, Ссылка) — компактные 40px. Из-за
  единой высоты кнопки визуально "раздувались" и теряли пропорции
  относительно инпутов — сейчас `TextInput` берёт высоту от `corner`
  (`panel` → 48px, `field` → 40px), `Button`/`Stepper` — фиксированные
  40px.
- **Радиус/срез угла.** Первая оценка (16px/16px) была примерно вдвое
  завышена. После прямого трейсинга пикселей и уточнения: скругление —
  **6px**, срез (chamfer) — **12px**.
- **Реальный баг: кнопки визуально "сплющивались".** `NotchedPanel`
  — это два вложенных `div` (внешний красит рамку/градиент, внутренний —
  заливку), и НИ ОДИН из них не имел собственной высоты — только
  padding. Когда `Button` ставил высоту на `<button>` (h-10 = 40px), эта
  высота физически не докатывалась до видимой панели: обычный блочный
  `div` не наследует высоту родителя просто потому, что у родителя она
  задана — а `h-full` внутри цепочки упирался в "невидимого" родителя
  без explicit height и схлопывался до высоты строки текста (~20px).
  Кнопка как элемент была 40px, а нарисованная рамка/срез внутри —
  вдвое тоньше. `TextInput` эту проблему не ловил, потому что высоту
  задавал напрямую на `<input>` (листовой элемент), в обход всей цепочки.
  Фикс — `NotchedPanel`'s внешний div теперь сам `h-full` по умолчанию,
  поэтому высота родителя (кнопки, степпера) корректно докатывается до
  видимой панели. Проверено не на глаз: сверял bounding box самого
  `<button>` и bounding box первого `div` с `clip-path` внутри него
  через Playwright — до фикса они расходились, после — совпадают.
- **Зазор между секциями.** 24px, не 32px — тоже подтверждено дважды:
  и прямым замером по скрину (~25px), и данными Figma MCP.

## Структура

```
styles/globals.css              — цвета/токены как CSS-переменные (замерены из скрина)
lib/cn.ts                       — clsx + tailwind-merge хелпер
lib/notch.ts                    — генератор clip-path для 4 паттернов среза углов
hooks/useTelegramViewport.ts    — мост Telegram WebApp API → CSS-переменные
hooks/useAutosizeTextarea.ts    — scrollHeight-автогрув для TextArea
components/TelegramViewportBridge.tsx — клиентская обёртка над хуком выше,
                                   монтируется в layout, не "заражает" его use client
components/ui/NotchedPanel.tsx  — базовый двухслойный компонент "срезанная панель"
components/ui/                  — Card, TextInput, TextArea, ToggleSwitch, Stepper,
                                   Button, CountBadge, SectionHeader — всё поверх
                                   NotchedPanel
components/desk-create/         — секции формы (композиты)
app/CreateDeskPage.tsx          — сборка экрана целиком
app/layout.example.tsx          — пример монтирования в root layout (Server Component,
                                   экспортирует viewport — см. "Адаптивность" ниже)
tailwind.config.js              — v3.4 конфиг, сюда переехали токены из бывшего @theme
postcss.config.js               — tailwindcss + autoprefixer
```

Зависимости:
```bash
npm i clsx tailwind-merge lucide-react
npm i -D tailwindcss@^3.4.0 postcss autoprefixer
```

## Сверка с Figma MCP-выгрузкой

Дополнительно проверено против `figma-*.json/md`, которые прислал
пользователь. Часть данных там противоречила скриншоту (акцент
`#0FEE9E` вместо оранжевого, `border-radius: 999px` для кнопок вместо
среза углов, почти невидимая обводка) — эти файлы сами себя называют
"structured summary" сырых данных на 7+ экранов и внутренне
противоречивы (в одном файле радиус 24px, в другом 12/6/999px), так что
по цвету/форме углов решили доверять скриншоту, он и оказался
достоверным источником. Но часть данных подтвердилась и была применена:

- радиус скругления **6px** (было 16px — ошибка, поймана и исправлена)
- срез угла **8px** (было 16px)
- зазор между секциями **24px** (было 32px, теперь подтверждено дважды —
  и прямым замером, и Figma)
- шрифт **Inter/Inter Display** вместо системного стека
- `input-field-m`/`input-field-s` как два явных именованных компонента —
  подтверждает разделение высот 48px/40px, которое до этого было
  эмпирическим выводом без независимого источника

## Что осталось приблизительным

Скриншот — не исходник Figma, поэтому часть значений — лучшее
приближение по пикселям сжатого PNG, не точные токены дизайн-системы:

- **Цвета градиентов** (teal→gold на кнопках, amber/red на степперах) —
  сэмплились в угловой точке кривой, где сходится сразу диагональ среза
  и обводка; итоговый цвет в токенах чуть темнее/приглушённее, чем может
  быть в исходнике, из-за блендинга при рендере 1px обводки на сжатом
  PNG.
- **Кнопка «Добавить ссылку»** на скрине не показала градиент так же
  чётко, как «Добавить коллегу» — возможно, это просто ракурс сжатия
  1px-линии, а не разные стили. Сейчас у всех «Добавить…» кнопок
  градиент одинаковый; если в Figma он различается по кнопкам, поправить
  проще всего через проп `borderGradient` у `Button`.

Раз в проекте уже есть Framelink MCP-воркфлоу — быстрее всего снять эти
допущения через `download_figma_images` + visual diff по исходнику,
а не гадать дальше по PNG.

## Интеграция

1. Скопировать `styles/`, `lib/`, `hooks/`, `components/` в проект (пути
   импорта — `@/...`, поправь под свой `tsconfig.json`, если алиас
   называется иначе).
2. Импортировать `styles/globals.css` один раз в корневом layout (пример
   — `app/layout.example.tsx`).
3. Смонтировать `useTelegramViewport()` там же, один раз на сессию.
4. Положить `CreateDeskPage` в роут, например
   `app/(desk)/create/page.tsx`, заменить `console.log` в `onSubmit` /
   `onAddColleague` на реальные вызовы.

## Tailwind v3.4, не v4 — почему и что поменялось

Изначально это было собрано на Tailwind v4. Переехало на v3.4, потому
что v4 компилирует часть служебных переменных (`--tw-translate-x` и
подобные — их использует, например, `ToggleSwitch` и `translate-x-*` у
степпера) через нативные CSS `@property`-правила — это нужно v4, чтобы
такие переменные корректно типизировались и анимировались. Сам увидел
это в собранном `out.css`: `@property --tw-translate-x { syntax: "*";
... }`. `@property` — довольно свежая штука, и старые Android WebView
внутри Telegram (а именно там открывается TWA, не в обычном браузере)
поддерживают её нестабильно или не поддерживают вовсе. В десктопном
Chromium (в том числе headless, которым я гонял скриншоты для сверки)
она есть всегда, поэтому баг не был виден на этапе разработки — вылезал
бы только в реальном Telegram-клиенте на не самом новом Android.

Что изменилось физически:

- **Конфиг переехал из CSS в JS.** Вместо `@theme { --color-* }` внутри
  `globals.css` — `tailwind.config.js` с `theme.extend.colors`, где
  каждый токен указывает на ту же CSS-переменную
  (`accent: "var(--color-accent)"`). Сами переменные остались в
  `globals.css`, просто в обычном `:root { }` вместо `@theme`. Поэтому
  `bg-accent`, `border-line`, `text-text-muted` и все остальные утилиты
  компилируются в точности как раньше — по имени класса разницы нет.
- **`content` явно, а не автоматически.** В v4 файлы для сканирования
  ищутся сами; в v3.4 их нужно явно перечислить в
  `tailwind.config.js` → `content: []` — уже сделано под структуру
  этого пакета (`app/`, `components/`, `hooks/`). Если начнёте добавлять
  файлы в новые папки — впишите путь туда же, иначе классы из них молча
  выпадут при паддинге.
- **`translate-x-*` теперь через классический `transform`, не через
  CSS-свойство `translate`.** Это ровно то, что убирает зависимость от
  `@property` — `transform: translate(...) rotate(...) ...` работает
  на любом браузере с поддержкой CSS-трансформов вообще, то есть
  практически везде.
- **Компоненты почти не тронуты.** Все srez-углы, arbitrary-values
  (`h-[52px]`, `rounded-[10px]`, `translate-x-[26px]`) — работают в v3
  JIT identично v4, это тот же движок генерации по существу. Правки
  ограничились `globals.css` + два новых конфиг-файла.
- **`clip-path` + `border-radius` вместе** и **`left-0` для
  `translate-x-*`** (баг из ToggleSwitch, где элемент без явного `left`
  уезжал не туда) — это чистый CSS box-model, к версии Tailwind
  отношения не имеет, работает одинаково что в v3, что в v4.

Пересобрал и сверил визуально через настоящий Tailwind v3.4.19 (не
теоретически) — рендер пиксель-в-пиксель совпадает с версией на v4.

## PurgeCSS и минификация

Отдельный PurgeCSS не нужен и не подключён — это инструмент для
Tailwind v1/v2, когда фреймворк сначала генерировал ВСЮ палитру
утилит, а PurgeCSS потом вычищал неиспользуемое отдельным проходом.
Начиная с v3, движок Just-In-Time сам генерирует **только** те классы,
что реально нашёл в файлах из `content` — то есть "purge" уже встроен
в компиляцию, а не докручен сверху. Отдельный пакет `purgecss` в
зависимостях был бы мёртвым грузом.

Что реально влияет на размер бандла в этом стеке:

- **JIT-генерация по `content`** — уже включено, это и есть purging.
  Для справки: собранный `globals.css` под весь экран `desk/create`
  (все компоненты, все состояния) — **21.7KB** несжатым, **10.5KB**
  после `cssnano`, **3.1KB** в gzip. Это весь CSS для полноценной формы
  с десятком разных компонентов — расти особо некуда, там и так почти
  нечего резать.
- **Минификация — не нужно настраивать руками.** `next build`
  минифицирует CSS автоматически (Next.js использует встроенный
  `cssnano-simple` в проде) — `postcss.config.js` в этом пакете
  специально БЕЗ `cssnano`, чтобы не гонять минификацию дважды. Если
  когда-нибудь соберёте это вне Next.js (чистый Vite/esbuild-пайплайн) —
  тогда `cssnano` действительно нужно добавить в `postcss.config.js`
  самостоятельно, `npm i -D cssnano` и в `plugins: { cssnano: {} }`
  под `process.env.NODE_ENV === "production"`.
- **Vercel** (там задеплоен Moraleon, и скорее всего onitask туда же)
  добавляет gzip/brotli на уровне edge-сети поверх минификации — тоже
  ничего конфигурировать не нужно, это автоматика хостинга.
- **Шрифт Inter** — если подключаете через `next/font/google`, а не
  через `<link>` на Google Fonts, Next.js сам самохостит и субсеттит
  шрифт под используемые символы (кириллица + латиница в данном случае)
  и убирает лишний рендер-блокирующий запрос — это самый весомый
  реальный рычаг размера страницы в TWA на медленном мобильном
  соединении, весомее, чем что-либо из CSS-тюнинга выше.
- **`lucide-react`** — уже используется правильно: импорт поштучно
  (`import { Upload } from "lucide-react"`), а не всего пакета целиком —
  тришейкается сам, ничего докручивать не нужно.

## Адаптивность: почему "плохо масштабируется" и что поправлено

Две независимые причины, обе баги в примере интеграции, не в самих
компонентах:

1. **Не было viewport meta-тега вообще.** `app/layout.example.tsx` был
   целиком помечен `"use client"` — а Next.js читает `viewport`/
   `metadata` экспорты только из Server Component, так что тег
   `<meta name="viewport">` просто не рендерился. Без него мобильный
   браузер (и WebView Telegram) по умолчанию считает страницу
   desktop-шириной (~980px) и масштабирует её целиком, чтобы влезла в
   экран — отсюда и "плохо масштабируется": на деле это не масштабирование
   раскладки, а уменьшение картинки. Поправлено: `layout.example.tsx`
   больше не клиентский компонент, экспортирует `viewport = { width:
   "device-width", initialScale: 1, viewportFit: "cover" }`, а
   единственное, что реально нужно браузеру (`useTelegramViewport`),
   вынесено в отдельный маленький клиентский
   `components/TelegramViewportBridge.tsx`, монтируемый внутри layout —
   тот же результат, без "заражения" всего layout директивой
   `"use client"`.

   `viewportFit: "cover"` тут не декоративный — без него
   `env(safe-area-inset-*)` всегда возвращает `0` на айфонах с
   вырезом/Dynamic Island, то есть весь safe-area-код в
   `CreateDeskPage` был бы тихо неактивен именно на iPhone — отдельно от
   масштабирования, это вторая вероятная причина плохого вида на новом
   айфоне.

2. **Сама раскладка компонентов уже была тянущаяся.** Перепроверил явно
   (раньше сверял пиксель-в-пиксель только на одной ширине 390px):
   прогнал через настоящий Chromium на 360 / 375 / 393 / 430px
   (маленький Android → iPhone Pro Max) — нигде нет горизонтального
   переполнения, инпуты и кнопки просто становятся шире вместе с
   контейнером. Вёрстка была не виновата — виноват отсутствующий
   viewport-тег из пункта 1.

## Отступ сверху под UI Telegram

`CreateDeskPage` резервирует минимум **48px** сверху перед контентом,
даже если Telegram ещё не отдал реальный `contentSafeAreaInset` (это
бывает: до инициализации JS-моста на первом пейнте, на старых клиентах,
на Android, где этот API часто просто не приходит) — раньше отступ
целиком зависел от значения из API и мог оказаться нулевым, и контент
лип бы прямо к хедеру/кнопке "назад" Telegram. Сейчас:
`paddingTop: max(48px, var(--tg-content-safe-top))` — берётся большее:
либо гарантированные 48px, либо реальный safe-area, если он больше
(например, при развёрнутой Dynamic Island).

## Срез угла — снова 16px

Возвращено с 12px на **16px**. Значение одно, в `NotchedPanel.tsx`
(`notch={16}`), задокументировано тем же числом в `globals.css` — если
понадобится поменять ещё раз, менять в одном месте.

## Нюансы адаптива под Telegram Web App

- **100vh непредсказуем.** Источник истины — `WebApp.viewportStableHeight`,
  который `useTelegramViewport` пишет в `--tg-viewport-stable-height` по
  событию `viewportChanged`. Базовый fallback — `100dvh`.
- **Safe area — два слоя.** `env(safe-area-inset-*)` (вырез ОС) +
  `WebApp.contentSafeAreaInset` (свой UI Telegram поверх). В
  `CreateDeskPage` складываются, а не заменяют друг друга.
- **Зум инпутов на iOS.** Все поля — `text-base` (16px), иначе
  Telegram-вебвью на iOS зумит страницу при фокусе и раскладка с
  клавиатурой съезжает.
- **Sticky CTA vs нативный MainButton.** В макете кнопка «Создать доску»
  — часть скролла, не прилипающая; так и сделано. В проде для TWA
  обычно лучше `WebApp.MainButton` — не перекрывается клавиатурой.
- **Свайп вниз закрывает мини-апп.** `disableVerticalSwipes()` в хуке
  это гасит (Bot API 7.7+, на старых клиентах no-op).

## Функциональные детали

- Все поля/кнопки внутри секции дизейблятся, когда её тоггл выключен.
- Кнопка «Создать доску» неактивна, пока не заполнены «Название доски» и
  `@desk` — это осознанное решение поверх статического макета (в
  скриншоте кнопка всегда показана "включённой", т.к. это не
  интерактивный кадр).
- Степперы «1 день»/«3 дня» не дают порогам пересекаться (min/max друг
  от друга).
- Русская плюрализация «день/дня/дней» вынесена отдельной функцией
  (`dayLabel`) в `TrafficLightCard`.

## Лимиты: название доски, @desk, документы

- **Название доски — максимум 21 символ.** `maxLength={21}` на
  `TextInput`, обычный нативный лимит браузера.

- **`@desk` — максимум 4 символа в редактируемой части.** Тут была
  неоднозначность в формулировке: сам плейсхолдер `@desk` — 5 символов
  с учётом `@`, а лимит просят 4. Решил так: `@` — фиксированный,
  не редактируемый префикс поля (так обычно делают в handle-полях в
  принципе), а лимит в 4 символа — на то, что после него (`desk` — как
  раз ровно 4 буквы, значит пример точно укладывается в лимит). Если на
  самом деле имелось в виду "5 символов ВСЕГО, включая `@`" — это одна
  строка отката: убрать `prefix="@"` у `TextInput` в
  `BasicInfoSection.tsx`, вернуть `placeholder="@desk"` и поставить
  `maxLength={4}` как обычный атрибут (тогда лимит станет 4 на всё
  поле целиком, включая `@`).

  Реализация: `TextInput` получил новый опциональный проп `prefix` —
  рисует статичный, не выделяемый текст перед полем ввода (не часть
  значения инпута). `@desk`-поле хранит в состоянии только саму ручку
  (`slug`, без `@`), очищает вставленный текст от случайных `@` в
  начале и обрезает до 4 символов вручную в `onChange`
  (`value.replace(/^@+/, "").slice(0, 4)`) — не полагаясь на нативный
  `maxLength`, потому что тот считал бы длину неправильно, будь `@`
  частью значения поля.

- **Документы — реальный баг, не просто отсутствие лимита.** До этой
  правки логика на самом деле УЖЕ поддерживала до 10 файлов
  (`<input multiple>` + `slice(0, 10)` в стейте) — но UI показывал
  только имя *последнего* выбранного файла и никак не отображал
  остальные. Прикрепить 5 файлов технически получалось, но выглядело
  так, будто прижился только один — предыдущие как будто исчезали.
  Поправлено: под полем-пикером теперь настоящий список всех
  прикреплённых файлов (тот же паттерн, что и у списка ссылок в этой же
  форме) — каждый файл отдельной строкой с кнопкой удаления, плюс
  счётчик `N/10` рядом с подсказкой про лимит, плюс поле-пикер и кнопка
  «Добавить .md файл» дизейблятся по достижении 10. Дедупликация по
  имени+размеру — повторный выбор уже прикреплённого файла не
  задваивает его в списке.

  Проверено не визуально, а через Playwright: прикрепил 9 файлов →
  список показал ровно 9 строк, бейдж `9/10`; докинул ещё 3 (стало бы
  12) → список остался на 10, бейдж `10/10`, кнопка «Добавить .md файл»
  стала disabled.

- **Контекст доски — максимум 1200 символов + поле теперь реально
  растёт, а не превращается в бесконечную строку.** До этой правки
  «Краткое описание» было однострочным `<input>` — при вставке длинного
  текста он не переносился, а просто скроллился горизонтально в
  невидимую бесконечность, перепроверить вставленное было невозможно
  без выделения-и-копирования обратно. Ещё когда сверял со скачанной
  Figma-выгрузкой раньше, там этот же элемент значился как отдельный
  компонент `text-area-m`, а не однострочное поле — тогда просто
  зафиксировал это наблюдение в README, сейчас довёл до кода.

  Новый `components/ui/TextArea.tsx` — та же визуальная система, что и
  у `TextInput` (тот же `NotchedPanel`, тот же срез углов, тот же
  `text-base` против iOS-зума), но рендерит `<textarea>` и растёт по
  высоте под контент через `hooks/useAutosizeTextarea.ts` — классический
  приём "сбросить высоту в auto, затем выставить по `scrollHeight`".
  Специально не через новое CSS-свойство `field-sizing: content` (это
  сделало бы то же самое вообще без JS) — оно слишком свежее для старых
  Android WebView внутри Telegram, та же логика, из-за которой раньше
  уходили с Tailwind v4 на v3.4.

  Рост ограничен потолком **40vh**, дальше — обычный внутренний скролл
  самого поля. Это осознанное решение, не часть исходного запроса:
  1200 символов — это условно 15–20 строк текста, и дать полю расти
  вообще без потолка означало бы, что при вставке текста близко к
  лимиту кнопка «Создать доску» может уехать на экран или два вниз.
  40vh — это всё ещё достаточно, чтобы перепроверить вставленный текст
  почти целиком без скролла, а на остаток есть скролл внутри самого
  поля, а не по всей странице. Если нужен рост вообще без потолка —
  это две строки в `TextArea.tsx`: убрать `max-h-[40vh]` и
  `overflow-y-auto` из className.

  Пустое поле по высоте (48px) специально совпадает пиксель-в-пиксель
  со старым однострочным полем — с виду ничего не «скакнуло», разница
  проявляется только когда реально печатаешь/вставляешь текст. Под
  полем — ненавязчивый счётчик `N/1200` (обычный текст, не пилюля, как
  у бейджа документов — в исходном макете под этим полем нет
  подсказки-хинта, так что лучше было не выдумывать новый визуальный
  паттерн, а обойтись минимальной подсказкой).

  Проверено через Playwright, не на глаз: пустое поле — 48px; короткая
  строка — тоже 48px; текст на 720 символов — поле выросло до 480px,
  горизонтального скролла нет (`scrollWidth - clientWidth = 0`); ввод
  2000 символов — сохранилось ровно 1200; текст на 1200 символов —
  высота упёрлась в потолок 480px (=40vh при высоте экрана 1200px) и
  включился внутренний скролл (`scrollHeight 888 > clientHeight 480`).

## Флоу спринтов: Create / Edit / View + модалка выбора дат

Новый флоу по трём макетам (IMG_6734/6733/6732) — «Создание спринта»,
«Редактирование спринта», просмотр активного спринта — плюс кастомная
шторка выбора диапазона дат вместо нативного календаря.

### Структура

```

components/ui/BottomSheet.tsx      — общий примитив шторки (портал + бэкдроп + анимация)
components/ui/Calendar.tsx         — сетка месяца с подсветкой диапазона
components/ui/DateRangeSheet.tsx   — шторка выбора дат (стек поверх другой шторки)

components/ui/ProgressBar.tsx      — прогресс-бар спринта
```

### Новый паттерн угла: `sheet`

Замерил по скринам, не на глаз: шторка — edge-to-edge (без боковых
отступов, `x: 0 → 780` на всю ширину), верхние углы срезаны на те же
~16px, что уже используются в остальной системе (совпало, отдельного
токена заводить не пришлось), низ — идеально прямой (шторка прижата к
краю устройства). Добавил в `lib/notch.ts` четвёртый паттерн `sheet`
(срез только TL+TR), а в `NotchedPanel` — проп `squareBottom`: без него
нижние углы шторки слегка скруглялись бы общим радиусом наравне с
остальными панелями, что выглядело бы как случайный нарост ровно на
грани экрана, а не бесшовное примыкание к ней.

### Новый цвет: `--color-success`

`#00E275` — статусный зелёный (бейдж «Активный», зелёная цифра «7/12»,
заливка прогресс-бара), отдельный от `--color-accent` (оранжевый).
Оранжевый остаётся за первичными действиями и маркерами секций, зелёный
— чисто семантический сигнал «активно/выполнено». Это не противоречит
более ранней истории с конфликтующим Figma-цветом `#0FEE9E` для
desk-create (тогда я доверился скриншоту, а не Figma-выгрузке) — просто
другой контекст, другой цвет, оба легитимны одновременно.

### Реальное несоответствие в макете: прогресс-бар vs подпись «61%»

При замере IMG_6732 заливка прогресс-бара оказалась примерно на 15% от
трека, а рядом подпись говорит «61%» — то есть **в самом макете** это
не совпадает. Не стал натягивать компонент пиксель-в-пиксель под это
конкретное (внутренне противоречивое) состояние — `ProgressBar`
получает реальный `percent` как проп и рисует заливку от него, а не от
фиксированного значения. Это единственно верный инженерный вариант, раз
число живое и будет меняться от спринта к спринту.

### Допущения, которые стоит перепроверить с вами

Часть решений — не вычитана из макетов (там просто не было нужного
состояния/кадра), а достроена по инженерной логике. Отмечаю явно, чтобы
было проще поправить, если что-то не так:

- **«Задачи спринта» в развёрнутом виде.** Ни один макет не показывает
  раскрытое состояние этого аккордеона (только «0 задач» свёрнуто).
  `TasksAccordionRow` — рабочий тоггл (шеврон крутится, блок
  раскрывается), но внутри — заглушка «Пока нет задач в спринте» и
  опциональный слот `children` для реального содержимого. Когда решите,
  что там на самом деле должно быть (список задач? кнопка добавления?
  выбор из бэклога?) — это чистая замена содержимого одного компонента,
  вся раскрывающая механика уже готова.
- **Условие активности кнопки «Создать спринт»/«Сохранить спринт».**
  В макетах кнопка везде показана в «включённом» виде (это статичные
  кадры, не интерактивное состояние) — как и в desk-create раньше,
  сделал разумное предположение: обязательны название + полный диапазон
  дат, цель и ёмкость — опциональны.
  «Ёмкость спринта» есть только в Create, в Edit её нет — сохранил эту
  асимметрию как есть, а не «починил» на симметричную: это похоже на
  согласованное с реальной архитектурой onitask поведение (rolling
  velocity-based capacity, а не ручное число, которое можно
  редактировать в любой момент).
- **`isActive` в `SprintViewSheet`.** Бейдж «Активный» управляется
  пропом снаружи, а не встроенной логикой по датам — в макете видно
  только один (активный) статус, других состояний (завершён/архивный) в
  скриншотах нет, поэтому не стал додумывать чужую логику статусов.

### Модалка выбора дат: что выбрал и почему

Кастомная шторка-календарь вместо нативного `<input type="date">`, по
трём причинам:

1. Поле хранит **диапазон**, не одну дату — у нативных пикеров нет
   концепции диапазона вообще, пришлось бы городить два отдельных
   нативных инпута, что на маленьком экране легко приводит к путанице
   "какую дату сейчас редактирую".
2. Нативные date-инпуты в Android WebView внутри Telegram рендерятся
   светлой системной темой поверх тёмного интерфейса — тот же класс
   проблем, из-за которого раньше в проекте уже уходили от хрупких
   нативных элементов (см. разделы про Tailwind v4→v3.4 и textarea
   autosize).
3. Схема "тап на первую дату → тап на вторую → дни между подсвечены"
   (как в Airbnb/букинг-сайтах) — стандартный, наименее подверженный
   ошибкам способ ввода диапазона на тачскрине; всегда видно, что уже
   выбрано, в отличие от двух текстовых полей.

Шторка дат открывается **поверх** шторки Create/Edit (`stacked` проп у
`BottomSheet`, z-50 против z-40 у обычной шторки), а не заменяет её
содержимое — так меньше хореографии переходов и понятнее, куда
вернёшься после отмены/подтверждения. Реализация без внешних
UI-библиотек (никаких react-day-picker/vaul) — весь календарь и шторка
на голом React + Tailwind, той же рукой, что и весь остальной проект.

### Механика: почему у `SprintCreateSheet`/`SprintEditSheet` проп `key` в примере

`BottomSheet` держит своих детей смонтированными даже когда закрыт (иначе
не на чём было бы играть анимацию закрытия) — значит внутренний
`useState` формы сам не сбросится просто от того, что `open` снова стал
`false`. В `app/SprintFlowPage.tsx` это решено явным инкрементом `key`
именно в момент, когда нужна гарантированно чистая форма (открытие
Create с нуля, открытие Edit с новыми исходными данными) — React
пересоздаёт компонент с нуля при смене `key`. Проверено вживую через
Playwright: заполнил и отправил форму Create, открыл Edit — поле
предзаполнено правильным (только что созданным) значением, не старым.

### Что проверено (не на глаз)

Собрал и прогнал весь флоу через настоящий Chromium (esbuild + реальный
Tailwind v3.4 CLI, без диффа с макетом на глаз — через Playwright):
заполнение Create → открытие шторки дат поверх → выбор диапазона тапами
→ «Готово» → значение подставилось в поле в формате `dd.mm.yyyy —
dd.mm.yyyy` → сабмит Create → переход в View с правильным именем,
бейджем «Активный» и целью → открытие Edit через иконку карандаша →
поле предзаполнено → изменение имени → сохранение → View отражает новое
имя. Отдельно проверил: z-index стекинг шторок (`z-40`/`z-50`) корректный,
горизонтального переполнения с открытым календарём нет, сетка календаря
укладывается в 390px, а на низком экране (600px) шторка View не
обрезает контент — включается внутренний скролл
(`scrollHeight 545 > clientHeight 510`), а не потеря нижней части формы.
