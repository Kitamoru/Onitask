# onitask · Agent Runtime (CLI Runner) — Vision & Decision Doc

**Версия:** 1.0.0
**Дата:** август 2026
**Статус:** Утверждено к разработке (Supervisor-архитектура)

> Тип документа: продуктово-техническое решение. Фиксирует: зачем Runner,
> что он делает и чего не делает, бюджет сопровождения с мерами снижения
> (встроены в чеклисты приёмки), план консолидации REST→MCP.
> Связанные: [[onitask_mcp_contract_]] · [[onitask_product_vision]] · Master §6.19

---

## 1. Решение (TL;DR)

1. **Runner = супервизор, а не AI-кодер.** Получает задачу из onitask,
   запускает headless-исполнителя в репозитории пользователя (`claude -p`,
   Codex CLI, …), двигает задачу по флоу (claim → review → деплой после апрува).
   Философия Control Plane сохраняется: **onitask управляет — исполнитель исполняет**.
2. **MCP остаётся единственным транспортом** (REST `/api/agent/*` замораживается,
   sunset по плану §7). Runner — флагманский *потребитель* MCP, не третий протокол.
3. **Формат поставки v0: npm-only**, Node ≥ 20. Без бинарников, автoupdate
   и нативной упаковки — минимизация регулярных затрат (§6).
4. Онбординг-поверхность: переключатель шаблонов подключения `MCP | CLI`
   (MCP по умолчанию). Curl-шаблоны REST уходят из UI в доки.

## 2. Рамка: слои системы

```
ПОТРЕБИТЕЛИ     Cursor / Cline / Claude Code / CI / RUNNER
ТРАНСПОРТ       MCP JSON-RPC (единственный, долгосрочно)
ДОМЕН           lib/domain/agent/* (claim, version, quota, deploy policy)
```

Runner нельзя «вместо» транспорта — ему нужно с чем-то говорить.
Замене подлежит: (а) второй транспорт REST — консолидируется в MCP;
(б) способ подключения «скопируй конфиг в IDE» — дополняется Runner'ом
как вариантом для headless-сценариев.

## 3. Юзер-кейсы

> Пересмотрены после принятия Supervisor-архитектуры (вариант C):
> экономика исполнения смещается к пользователю (BYOE — bring your own
> executor), а супервизор получает управление НАД исполнением — отсюда
> новые кейсы UC-8…10 и уточнение стоимости в UC-4.

### Включённые (приоритеты P0–P3)

| UC | Сценарий | Приоритет |
|---|---|---|
| UC-1 | «Ночной разработчик»: агент 24/7 на сервере берёт задачи, запускает headless-исполнителя, к утру — карточки на ревью в Telegram, апрув → деплой. Супервизор перезапускает упавшего исполнителя | **P0** |
| UC-5 | «Дежурство без спящего хоста»: надёжный loop + heartbeat + статус «на смене / офлайн»; рестарт исполнителя — тоже зона супервизора | **P0** |
| UC-10 | «Бюджетный щит»: лимиты на агента (задач/ночь, стоп по стоимости исполнения) поверх чужих платных исполнителей — развитие F-01 Cognitive Budget на агентную экономику | **P1** |
| UC-7 | «Демо за 60 секунд»: `npx @onitask/agent start` вместо настройки IDE | P1 |
| UC-4 | «Команда без рабочих мест»: VPS + подписка исполнителя (Claude Code / API-ключ) = цифровой сотрудник. Требует уже оплаченного AI-кодинга — сегмент платёжеспособный, но НЕ «$5 всего» | P1 |
| UC-8 | «Умная эскалация»: исполнитель упал/ушёл не туда → retry другим исполнителем, возврат задачи или escalate человеку с контекстом — никогда не молчаливый провал | P2 |
| UC-2 | «Ферма агентов»: N супервизоров с разными autonomy_level И разными исполнителями как команда воркеров | P2 |
| UC-9 | «Тендер исполнителей»: одна задача — двум исполнителям, оба diff'а на ревью, человек выбирает лучший (review-центричное дифференцирование) | P3 |
| UC-3 | «CI-исполнитель»: одноразовый прогон `run-once --take-tagged ci-fix` (auth исполнителя через ENV CI) | P3 |
| UC-6 | «Self-hosted контур»: docker, data_sharing=minimal, код не покидает периметр | P3 |

### Анти-кейсы (осознанно НЕ делаем)

- Управление ключами/досками из терминала — дублирует TWA (отклонено ранее).
- Своя LLM-интеграция кодогенерации — второй продукт, проигрывает Cursor.
- **Биллинг/субсидирование исполнения пользователей** — токены всегда
  оплачивает владелец исполнителя (BYOE); мы никогда не посредник по платежам.
- **Облачная песочница для чужих репозиториев в v0-v1** — исполнение строго
  на машине пользователя; SaaS-execution требует инфраструктуры другого класса.
- Разовые операции из скриптов — покрываются MCP напрямую.
- Нативные сборки (exe/msi) до измеренного спроса.

## 4. Ключевое архитектурное решение: Supervisor

```
┌────────────────────────── onitask (cloud) ──────────────────────────┐
│  MCP transport ← домен: wait_for_tasks, move_task, escalate, …      │
└──────────────▲──────────────────────────────────────────────────────┘
               │ MCP (Bearer key, X-Agent-Name)
┌──────────────┴──────────────────── RUNNER (у пользователя) ─────────┐
│  Duty Loop:  wait_for_tasks → claim → DELEGATE → report → review    │
│                      │                                              │
│              EXECUTOR PLUGIN                                        │
│              ┌───────┴────────┐                                     │
│              │ claude -p      │  (v0 — единственный адаптер)        │
│              │ codex (v1)     │  интерфейс плагинный с первого дня  │
│              └────────────────┘                                     │
│  Политики: playbook из get_workspace_settings (autonomy level),     │
│  retry/backoff §7, fail-loud в TG-чат, санитизация логов            │
└─────────────────────────────────────────────────────────────────────┘
```

**Контракт исполнителя (plugin interface):**
`execute(task: {full_id, title, description, repo_path}) → {status, summary}`
— v0 реализация: spawn `claude -p "<task>"` в repo_path, парсинг результата.
Никакой логики onitask внутри плагина — смена вендора не трогает ядро.

**Чего Runner сознательно НЕ делает (v0):** не хранит LLM-ключи (их хранит
исполнитель), не пишет код сам, не управляет ключами/досками, не обновляется
автоматически (обновление = `npm update -g`), не биллит исполнение
(BYOE — токены оплачивает владелец исполнителя).

**Супервизорские обязанности поверх плагина (следствие варианта C):**
рестарт упавшего исполнителя, тайм-ауты исполнения, retry ≤ N →
`escalate_task` с контекстом (UC-8), бюджетные стоп-краны (UC-10).
Использование headless-исполнителя документируется в least-privilege
режиме (`--permission-mode`, allowlist команд).

## 5. Обязательства совместимости (жёсткие правила)

1. Неизвестные поля контракта раннер **молча игнорирует** — старые версии
   живут при новых полях (паттерн jsonb-конфигов).
2. Ключ — только ENV (`ONITASK_KEY`) или keychain. Никогда в argv, файлах
   и логах. Логи санитизируются на стороне раннера (sk_* → `sk_***`).
3. Semver пакета; breaking-изменения только с мажорной версией и заметкой
   в mcp_contract changelog.

## 6. Бюджет сопровождения и чеклисты приёмки

Оценка регулярных затрат: v0 ≈ 1–2 недели разработки + **2–4 дня/мес**
эксплуатации; рост от числа установок.

Каждая мера снижения — проверяемый критерий приёмки v0:

- [ ] **AC-1 npm-only**: установка = `npm i -g @onitask/agent`; нет постинсталл-скриптов.
- [ ] **AC-2 fail-loud**: крах процесса → `send_message_to_chat` в привязанный чат
      воркспейса («агент <name> упал: <причина>») до завершения процесса.
- [ ] **AC-3 секреты**: ключ читается только из ENV/keychain; grep по логам
      не находит полного ключа; ключ отсутствует в `ps`/argv.
- [ ] **AC-4 совместимость**: фиктивный ответ API с неизвестными полями не
      ломает цикл (тест unknown-fields tolerance).
- [ ] **AC-5 плагинность**: исполнитель заменяется конфигом без изменения ядра
      (интерфейс задокументирован, один адаптер claude-code).
- [ ] **AC-6 уровни автономии**: observer-ключ физически не может вызвать мутации
      (403 от сервера → штатная остановка, не retry-буря).
- [ ] **AC-7 телеметрия онбординга**: фиксируется вариант первого успешного
      подключения (MCP-конфиг vs CLI) — данные для решения о развитии.
- [ ] **AC-8 провал исполнителя**: executor упал/тайм-аут → задача не зависает:
      retry ≤ N → `escalate_task` с контекстом; молчаливое зависание исключено.
- [ ] **AC-9 минимальные привилегии**: раннер запускает исполнителя только в
      задокументированном least-privilege профиле (permission-mode/allowlist).
- [ ] **AC-10 бюджетный стоп-кран**: лимиты (задач за смену, макс. время
      исполнения) исчерпаны → агент корректно завершает смену и сообщает в чат
      (фундамент UC-10 «Бюджетный щит»).

## 7. Консолидация REST → MCP (deprecation plan)

| Этап | Действие | Срок |
|---|---|---|
| Сейчас | `/api/agent/*` frozen: новые поля — только в MCP-контракте; curl-шаблоны уходят из TWA в доки | немедленно |
| Наблюдение | счётчик внешних вызовов REST | 30 дней |
| Sunset | `Sunset` header + миграционная заметка в changelog | окно 90 дней |
| Удаление | удаление тонкой REST-обёртки (домен общий — переписывания нет) | после окна |

Удаление выполняется отдельным изменением контракта **после** стабилизации
Runner v0 — не одновременно с его выпуском.

## 8. Roadmap

- **v0 (P0):** runtime skeleton (ENV-конфиг, duty-loop, playbook-fetch),
  executor-адаптер claude-code, flow-интеграция (claim→review→деплой после
  апрува для full), fail-loud, санитизация логов, AC-1…7.
- **v1 (P1):** публикация в npm + CLI-таб в шаблоне подключения активен,
  heartbeat + статус «на смене» в Flow Board, телеметрия онбординга,
  бюджетные стоп-краны (UC-10, развитие F-01 на агентную экономику).
- **v2 (P2–P3):** умная эскалация с retry между исполнителями (UC-8),
  run-once режим для CI (UC-3), второй executor (codex), docker-образ,
  тендер исполнителей (UC-9), мультиагентная ферма (документация + примеры).

Критерий старта v1: ≥3 активных duty-сессии через Runner от реальных
пользователей в течение двух недель после v0.
